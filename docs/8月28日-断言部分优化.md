## 0. 调度：前置先跑，步骤与预期按编号对照

用例三列职责不变。对照规则改成 **按编号 JOIN，不是按下标 1、2、3 硬配**：

| 列 | 含义 | 执行器职责 |
|----|------|------------|
| **前置** | 环境能不能开跑 | **整段先跑完**。库外 / 做不到 **跳过并打标签**，不挡步骤。只有真实检查没过（未登录等）才停 |
| **测试步骤** 1,2,3… | 编号操作 | 按步骤编号依次做。自愈只发生在本步内 |
| **预期** | 与步骤 **同号** 才验 | 预期列可以缺号。只有 `1 3 4` → **步骤 2 做完后不验**，直接进步骤 3 |

主循环：

```
前置先跑。UNKNOWN / UNSUPPORTED → 跳过并打「无法执行/无法识别」标签，不挡开跑
         UNMET / FAIL → 停（真实检查和预期不符）
  → for n in 测试步骤编号（按号升序）:
        执行 测试步骤 n（可自愈）
        若步骤 n 未做成 → 本步及之后步骤、仍未验的预期一律 SKIPPED，结束
        若预期列没有编号 n → 不验证，记 EXPECT.SKIPPED.no_expect，进 n+1
        若预期列有编号 n → **不走操作 prompt**，按质检库分类：
           命中 → 只把可核片段交给 assert_visual
           FAIL → 校验不通过，停；后面未跑的记未观察，不当失败
           UNVERIFIABLE / UNKNOWN → 记无法验证并继续，不算产品失败；整单不算通过
           一条里既有「进入首页」又有「选中态」→ 只验前者，后者跳过
        再进入步骤 n+1
  → 汇总覆盖码
```

示例（预期只有 1、3、4）：

| n | 测试步骤 | 预期列有无 n | 本步之后 |
|---|----------|--------------|----------|
| 1 | 做 | 有 | 验预期 1 |
| 2 | 做 | **无** | **跳过验证**（`EXPECT.SKIPPED.no_expect`），不是无法验证 |
| 3 | 做 | 有 | 验预期 3 |
| 4 | 做 | 有 | 验预期 4 |

禁止：

- 把预期第 2 行（原文编号是 3）配到步骤 2 上——现在 `to_case_spec` 在缺 `expected_by_step` 时会按下标对齐，落地时必须改成 **只按编号**。
- 用「整段 goal 跑完再看总图」代替逐步对照。
- 前置做不到、预期验不了时用自愈凑绿。

自愈只发生在 **测试步骤**。前置 / 预期禁止自愈。

## 1. 覆盖类与状态码

### 1.1 三列结果必须能拆出 UNKNOWN

每一列先匹配 **当前引擎库**（见 §2 / §3 / §4 的 kind 表）。匹配结果只有两类：

| 匹配 | 含义 |
|------|------|
| **命中库** | 知道这是哪一种前置 / 能力 / 质检，再谈 OK / 失败 / 明确做不到 |
| **UNKNOWN** | **和现在库匹配不上**：分不出 kind，不知道该调哪条检查、哪个 capability、哪种断言 |

UNKNOWN **不是** UNSUPPORTED / UNVERIFIABLE 的别名：

| | UNKNOWN | UNSUPPORTED / UNVERIFIABLE |
|--|---------|------------------------------|
| 引擎知不知道「这是什么」 | 不知道 | 知道，且判定本引擎不做 / 不验 |
| 典型 | 「确保活动在灰度且运营位已排期」 | 「查看 Web 后台开关」「入场动画流畅」 |
| 后续动作 | 补分类器或改用例写法 | 补能力，或接受覆盖缺口 |

三列都要有独立 UNKNOWN 码：`PREP.UNKNOWN` / `STEP.UNKNOWN` / `EXPECT.UNKNOWN`。报表按列拆，不要揉进一个 `generic`。

### 1.2 覆盖类 `coverage_class`（用例级，取「最严重」）

严重度从高到低。一条用例只落一个类。

| 覆盖类 | 中文 | 何时 | 产品红 |
|--------|------|------|--------|
| `pass` | 通过 | 该跑的步骤都做成；**有编号的预期**都能验且都过；库外/做不到已跳过 | 否 |
| `product_fail` | 校验不通过 | 步骤能做，对应预期 **能验** 但没过 | **是** |
| `prep_insufficient` | 执行期-前置准备不足 | 前置 **UNMET / FAIL**（真实检查没过） | 否 |
| `step_unexecutable` | 执行期-测试步骤无法执行 | 步骤 UNSUPPORTED / FAIL / **UNKNOWN** | 否 |
| `expect_unverifiable` | 无法验证 | 步骤做了，该号预期 UNVERIFIABLE 或 **UNKNOWN**，且没有 FAIL | 否 |
| `untestable` | 不可测 | 微信登录等已拍板 | 否 |
| `engine_error` | 执行期-引擎故障 | 截图失败、LLM 空输出 | 否 |

有 `EXPECT.FAIL` 时优先 `product_fail`，即使同条还有 UNVERIFIABLE。  
`EXPECT.SKIPPED.no_expect` **不参与** 覆盖类，也不算缺口。

### 1.3 覆盖度口径

```
步骤覆盖率     = (STEP.OK + STEP.HEALED) / 测试步骤条数

预期覆盖率     = (EXPECT.PASS + EXPECT.FAIL) / 有编号的预期条数
                 分母 = 预期列实际写出的编号，不含「步骤有、预期无」
                 SKIPPED.no_expect 不进分母

有效质检率     = 同上分子 / 有编号的预期条数

库命中率       = 非 UNKNOWN 的前置+步骤+有编号预期 / 这三类总条数
缺口率         = UNSUPPORTED + UNVERIFIABLE + UNKNOWN（各列）条数占比
UNKNOWN 率     = 三列 UNKNOWN 条数 / 对应列总条数（分列看）
```

`product_fail` 只来自 **能验证却没过**。UNKNOWN / UNVERIFIABLE 拉高缺口，不拉失败率。

### 1.4 `reason_code` 格式

`阶段.结果.原因`。UNKNOWN 时原因可空或填 `unmatched`：`PREP.UNKNOWN` / `PREP.UNKNOWN.unmatched`。

前缀：`PREP.` / `STEP.` / `EXPECT.`

## 2. 前置操作（优先、全部完成才进步骤）

### 2.1 当前库（命中后才能 OK / UNMET / FAIL / UNSUPPORTED）

与 `case_precondition_service._classify_line` 对齐，写作必须尽量用这些说法：

| kind | 原文关键词（命中库） | 成功 | 不满足 / 失败 |
|------|----------------------|------|----------------|
| 清缓存 | 无缓存、清除缓存、清理缓存、清空缓存、清缓存、清除应用 | `PREP.OK.clear_cache` | `PREP.FAIL.clear_cache` |
| 检查 SIM | SIM卡、安装 SIM、手机卡、电话卡 | `PREP.OK.sim` | `PREP.UNMET.sim` |
| 已装微信 | 安装微信、已装微信、有微信 | `PREP.OK.wechat` | `PREP.UNMET.wechat` |
| 未装微信 | 未安装微信、没装微信、无微信 | `PREP.OK.no_wechat` | `PREP.UNMET.wechat` |
| 平台 iOS | iOS / 苹果机 + 设备/手机 | `PREP.OK.platform` | `PREP.UNMET.platform` |
| 平台 Android | 安卓 / Android + 设备/手机 | `PREP.OK.platform` | `PREP.UNMET.platform` |
| 已登录 | 已登录、登录状态、保持登录 | `PREP.OK.session` | `PREP.UNMET.session` |
| 游客 | 未登录、游客、未登陆 | `PREP.OK.session` | `PREP.UNMET.session` |
| 保留权限询问 | 保留权限询问、不要预授权、keep_permission | `PREP.OK.keep_permission` | — |
| 亮屏解锁 | 预置，不必写在用例里 | `PREP.OK.awake` | `PREP.FAIL.awake` |
| Android grant | 预置 | `PREP.OK.grant` | 漏网框算步骤自愈 |

iOS 查 SIM：现码 skip-pass。新规则 **`PREP.UNSUPPORTED.sim_ios`**（已识别 kind=check_sim，平台做不到），**不是** UNKNOWN。

登录：前置写了已登录、设备在登录页 → `PREP.UNMET.session`。微信-only → `untestable`。

### 2.2 命中库但明确不能做 → UNSUPPORTED

| 类型 | reason_code |
|------|-------------|
| 查 Web / 运营后台 | `PREP.UNSUPPORTED.web_config` |
| 查服务端开关 / 远程配置 | `PREP.UNSUPPORTED.remote_config` |
| 造指定服务端数据 | `PREP.UNSUPPORTED.backend_data` |
| 真短信（无固定码） | `PREP.UNSUPPORTED.sms_live` |
| 接电话 / 推送必达 | `PREP.UNSUPPORTED.external_channel` |
| 地理围栏 / 时间旅行 | `PREP.UNSUPPORTED.device_mock` |
| iOS 读 SIM | `PREP.UNSUPPORTED.sim_ios` |

这些句子要能被分类器标成上表类型。分类器认不出 → 走 UNKNOWN，不要猜成 web_config。

### 2.3 匹配不上库 → PREP.UNKNOWN

| code | 何时 |
|------|------|
| `PREP.UNKNOWN` | `_classify_line` / 前置解析的 kind 仍是 `unknown`，或抽不出任何 kind |

现在 `unknown` / UNSUPPORTED 是 **跳过 + 标签**，不挡跑。禁止当成 PASS。`coverage_class` 仍由真实检查 / 验收决定。

### 2.4 前置状态码一览

| code | 含义 | 进步骤？ |
|------|------|----------|
| `PREP.OK.*` | 库内，已满足或已执行 | 本条通过 |
| `PREP.UNMET.*` | 库内，检查了不够 | 停 |
| `PREP.FAIL.*` | 库内，动作失败 | 停 |
| `PREP.UNSUPPORTED.*` | 库内，引擎不做 | **跳过**，打「无法执行」 |
| `PREP.UNKNOWN` | **未命中前置库** | **跳过**，打「无法识别」 |

仅 UNMET / FAIL → 整条 `prep_insufficient`。

## 3. 测试步骤

来源：`parse_numbered_field` / `step_nums`。禁止揉成一个模糊 goal。

### 3.1 当前操作库（命中后才能 OK / HEALED / FAIL / UNSUPPORTED）

| 能力 | capability | 步骤里应出现的动词 |
|------|----------|------------------|
| 点击 | `tap_element` | 点击、点、打开（按钮/入口） |
| 长按 | `long_press_element` | 长按 |
| 滑动（方向） | `swipe_direction` | 上滑、下滑、左滑、右滑 |
| 拖拽 | `swipe_element_to_element` | 拖到、拖拽（写清起点和终点） |
| 输入 | `input_text` | 输入、填写（文案写死或写「用账号包字段」） |
| 系统键 | `press_key` | 返回、按 Home |
| 启停应用 | `launch_app` / `close_app` / `kill_app` | 打开应用、关闭应用、杀进程 |
| 等待 | `wait_ms` | 等待 N 秒（写数字，有上限） |
| 剪贴板 | `set_clipboard` | 少用 |

自愈（仍算本步，不另开号）：弹窗、点偏重试一次、短加载。成功记 `STEP.HEALED.popup|retry|wait`。

### 3.2 命中「做不到」类型 → STEP.UNSUPPORTED

| 步骤类型 | reason_code |
|---------|-------------|
| 语音 / 视频通话 | `STEP.UNSUPPORTED.av_call` |
| 摄像头对着特定实物 | `STEP.UNSUPPORTED.camera_scene` |
| 双指缩放等复杂手势 | `STEP.UNSUPPORTED.gesture_complex` |
| 切到微信/支付宝支付闭环 | `STEP.UNSUPPORTED.external_app_pay` |
| 听声道、震动、闪光 | `STEP.UNSUPPORTED.hardware_fx` |
| 同时操作 Web 后台 | `STEP.UNSUPPORTED.cross_surface` |

### 3.3 匹配不上操作库 → STEP.UNKNOWN

| code | 何时 |
|------|------|
| `STEP.UNKNOWN` | 本步原文无法落到上表任一 capability，也无法落到 UNSUPPORTED 类型 |

例如：「完成一次完整下单并让运营审核通过」——不是点击，也不是已列的做不到类型，就是 UNKNOWN。

有能力但做失败：`STEP.FAIL.action` → 仍归 `step_unexecutable`（预期还没资格验）。

### 3.4 步骤推进 + 与预期对照

1. 步骤 n `running`。
2. 做成（OK / HEALED）后：
   - 预期 map 无 n → `EXPECT.SKIPPED.no_expect`，**立刻**步骤 n+1。
   - 有 n → 验预期 n，再 n+1。
3. 预期结果无论 PASS / FAIL / UNVERIFIABLE / UNKNOWN，默认继续下一步（`stop_on_expect_fail` 默认 false）。
4. 步骤 n 为 UNKNOWN / UNSUPPORTED → 本步打标签并跳过，**继续 n+1**。步骤 n 为 FAIL（真实没做成）→ 步骤 n+1… 与尚未执行的预期全部 `SKIPPED`。
5. 预期列出现步骤里没有的号（孤儿号）→ `EXPECT.SKIPPED.orphan_number`，不挡步骤执行。

### 3.5 测试步骤状态码一览

| code | 含义 |
|------|------|
| `STEP.OK` | 命中库并做完 |
| `STEP.HEALED.*` | 命中库，自愈后完成 |
| `STEP.FAIL.action` | 命中库，做失败 |
| `STEP.UNSUPPORTED.*` | 命中「做不到」类型 |
| `STEP.UNKNOWN` | **未命中操作库** |
| `STEP.SKIPPED.blocked` | 前序步骤挡住 |
| `STEP.SKIPPED.cancelled` | 任务取消 |

存在未自愈 FAIL → `step_unexecutable`。UNKNOWN / UNSUPPORTED 只记缺口标签，不改覆盖类。

## 4. 预期（只验有编号、且对应步骤已做成的）

预期 n **只在步骤 n 成功之后**跑。步骤没做成 → `EXPECT.SKIPPED.step_not_done`（不是无法验证，也不是产品失败）。

步骤有、预期无 → `EXPECT.SKIPPED.no_expect`（无需验证）。

一条有编号的预期可再拆 claim；**每个 claim 先对预期库**，对不上的 claim 记 UNKNOWN。

### 4.1 当前质检库（命中后才能 PASS / FAIL / UNVERIFIABLE）

与 `parse_expectation_claims` 的 kind + 执行能力对齐：

| 质检类型 | 写法（命中库） | 过 | 不过 |
|----------|----------------|----|------|
| 文本出现 | 出现「…」/ 可见文案「…」 | `EXPECT.PASS.text_present` | `EXPECT.FAIL.text_present` |
| 文本不出现 | 不出现「…」/ 不含「…」 | `EXPECT.PASS.text_absent` | `EXPECT.FAIL.text_absent` |
| 数量 | 数量为 N、显示 N（+1 必须有步骤前快照） | `EXPECT.PASS.numeric` | `EXPECT.FAIL.numeric` |
| 页面切换 | 进入/切换到/到达「某页」 | `EXPECT.PASS.page_nav` | `EXPECT.FAIL.page_nav` |
| 控件存在 | 「某按钮」可见 / 存在 | `EXPECT.PASS.node` | `EXPECT.FAIL.node` |
| 登录结果 | 进入首页 / 仍在登录页 | `EXPECT.PASS.login_outcome` | `EXPECT.FAIL.login_outcome` |
| 业务含义 | 一句话、可看静帧（领取球是礼） | `EXPECT.PASS.meaning` | `EXPECT.FAIL.meaning` |
| 粗布局 | 在底部/顶部、A 在 B 下方（有 dump） | `EXPECT.PASS.layout` | `EXPECT.FAIL.layout` |

`assert_visual` 只用于 **meaning**。不用于点哪里、等屏、整段成功标准。

现码里 LLM 还会给出 `generic`。落地后：**generic 且规则也对不上上表 → EXPECT.UNKNOWN**，不要再当弱断言乱 PASS。

### 4.2 命中「验不了」类型 → UNVERIFIABLE

| 类型 | reason_code |
|------|-------------|
| 动画、转场、跟手、粒子 | `EXPECT.UNVERIFIABLE.animation` |
| 视频自动播、声音、震动 | `EXPECT.UNVERIFIABLE.av_haptic` |
| 高级感、沉浸、好看 | `EXPECT.UNVERIFIABLE.subjective` |
| 必须连续多帧才成立 | `EXPECT.UNVERIFIABLE.temporal` |
| 无基线的 +1 / 从 A 变 B | `EXPECT.UNVERIFIABLE.no_baseline` |
| 像素级对齐、色值、字号 | `EXPECT.UNVERIFIABLE.pixel_perfect` |
| 底栏/页签选中态、高亮选中 | `EXPECT.UNVERIFIABLE.tab_selected` |

### 4.3 匹配不上质检库 → EXPECT.UNKNOWN

| code | 何时 |
|------|------|
| `EXPECT.UNKNOWN` | 该编号预期（或其中某 claim）对不上 §4.1，也对不上 §4.2 |

「功能正常」「逻辑正确」「与设计一致」没有可核对对象，一律 UNKNOWN。

无法验证 / UNKNOWN **都不是** PASS。分母算覆盖，通过率不算它们。

### 4.4 预期状态码一览

| code | 含义 | 算覆盖分母？ |
|------|------|----------------|
| `EXPECT.PASS.*` | 命中库且过 | 是 |
| `EXPECT.FAIL.*` | 命中库且不过 → 可贡献 product_fail | 是 |
| `EXPECT.UNVERIFIABLE.*` | 命中「验不了」类型 | 是（缺口） |
| `EXPECT.UNKNOWN` | **未命中质检库** | 是（缺口） |
| `EXPECT.SKIPPED.no_expect` | 该步骤号没有预期，按设计不验 | **否** |
| `EXPECT.SKIPPED.step_not_done` | 对应步骤没做成 | 否 |
| `EXPECT.SKIPPED.orphan_number` | 预期号在步骤列不存在 | 否 |
| `EXPECT.SKIPPED.blocked` | 前序步骤挡住未执行到 | 否 |

有 FAIL → `product_fail`。UNKNOWN / UNVERIFIABLE 只打「无法验证 / 无法识别」标签，不改覆盖类。

## 6. 和现在 Agent 怎么接

不恢复旧 Plan 盲排。三列是调度骨架。

```
前置：provision + run_preconditions + session_gate
      kind=unknown / UNSUPPORTED → 跳过并打标签，不挡跑
      UNMET / FAIL → 停跑
测试步骤 n：
      原文对操作库 → 一个 capability（VLM 只给本步坐标）
      对不上库、也对不上 UNSUPPORTED 表 → STEP.UNKNOWN，后面 SKIPPED
      失败 → 本步自愈有界；仍失败 → STEP.FAIL
预期：
      只跑 expected_by_step[n]；没有该 key → SKIPPED.no_expect
      禁止「第 i 条预期配第 i 个步骤」
      claim 对质检库分流 dump / OCR / meaning / UNVERIFIABLE
      对不上 → EXPECT.UNKNOWN，立刻返回，不看图硬判
```

`extract_goal` 不再把整段预期捏成一个 success_criteria。`done` = 步骤列表走完。  
`stop_on_expect_fail` 默认 false。

## 7. 用例写作准则（按当前库写，执行才对得上）

目标：少 UNKNOWN、少 UNSUPPORTED、该验的预期带对编号。生成草稿 / 人工改稿 / 飞书导入都按这张表。

### 7.1 结构

1. **三列分开写**，不要把检查环境写进步骤，不要把操作写进预期。
2. **前置整段先跑**；库外 / 做不到跳过并打标签，不挡开跑。需要 Web/造数的条件仍建议人工准备。
3. **步骤按 1. 2. 3. 编号**，一步一个主操作。
4. **预期编号 = 要校验的那个步骤号**，允许跳号。只有 1、3、4 就只写 1、3、4，不要补假的「预期 2」。
5. 一步多结果：拆成多个 claim 写在 **同一个编号** 下（分号分隔），或拆成多条用例；不要写成预期 2 对应步骤 1。

### 7.2 前置：只写库里的环境

**建议原文（可直接贴）：**

- `已登录` / `游客` / `未登录`
- `无缓存` 或 `清除应用数据`
- `已安装 SIM 卡`（仅 Android 有意义；iOS 会 UNSUPPORTED，不要用这条测 iOS）
- `已安装微信` / `未安装微信`
- `Android 设备执行` / `iOS 设备执行`
- `保留权限询问`（只有要测拒绝权限时才写）

**不要写进前置：**

- 查看后台 / 运营配置 / 远程开关 → `UNSUPPORTED`，打「无法执行」并跳过
- 「账号已购礼 / 指定订单」除非号池标签能对上；对不上就是 `backend_data`，同样跳过
- 活短信、真电话、定位造假 → 跳过
- 散文：「环境准备完毕」「数据正常」→ **PREP.UNKNOWN**，打「无法识别」并跳过

### 7.3 步骤：动词必须能落到 capability

每步用 **一个** 下表动词 + **界面上能指认的对象**（按钮文案、tab 名）：

| 要做的事 | 写成 |
|---------|------|
| 点 | `点击「立即领取」` |
| 长按 | `长按「消息」` |
| 滑 | `上滑一屏` / `下滑`（写方向，不要写「随便滑」） |
| 拖 | `将「A」拖到「B」` |
| 输入 | `在「手机号」输入 13800000000` |
| 返回 | `按返回键` |
| 启停 | `打开应用` / `杀进程后打开应用` |
| 等 | `等待 3 秒`（仅加载；不要用等待代替断言） |

**会 UNKNOWN 或 UNSUPPORTED 的写法：**

- 「完成下单流程」「按日常习惯操作」——没有单一 capability
- 「语音说打开领取」「对着二维码扫」
- 「去微信里付完再回来」
- 一步里塞三个点击（拆成 3 步，预期按号挂）

中间被挡（弹窗）不用写进用例，执行期自愈。

### 7.4 预期：有编号才验；写法要对质检库

**该验就写同号；不该验就空着。**

| 想确认 | 写成（同步骤号） |
|--------|------------------|
| 到了某页 | `进入首页` / `切换到「我的」页` |
| 某文案在 | `出现「领取成功」` |
| 某文案不在 | `不出现「网络错误」` |
| 数字 | `「积分」显示为 10`（不要只写「+1」，除非上一步能采基线） |
| 入口还在 | `「领取悬浮球」可见` |
| 含义（静帧） | `首页可见领取礼悬浮球`（一句，不要夹带动效） |

**不要写（会 UNVERIFIABLE 或 UNKNOWN）：**

- 动画流畅、转场自然、跟手、粒子、音效、震动
- 好看、高级、符合设计稿 4px
- 功能正常、逻辑正确、无异常
- 把三步的结果全堆在预期 1

动效如果产品非要记一笔：单独占一个预期号，例如只在步骤 3 写 `入场动画流畅` → 该号 `UNVERIFIABLE.animation`，不要和「出现领取球」写在同一句，以免整句被判 UNKNOWN 或误 PASS。

### 7.5 编号对照（必做）

```
测试步骤：
1. 打开应用
2. 上滑浏览推荐流
3. 点击「领取悬浮球」
4. 点击「立即领取」

预期效果：
1. 首页可见领取悬浮球
3. 出现领取弹窗
4. 出现「领取成功」
```

步骤 2 执行、不验证。执行器不得把「出现领取弹窗」配到步骤 2。

### 7.6 自检清单（保存前）

- [ ] 前置每一行都能在 §2.1 / §2.2 找到 kind，否则删掉或改成库内说法
- [ ] 每一步恰好一个表内动词 + 可指认对象
- [ ] 预期编号 ⊆ 步骤编号；缺的号表示不验
- [ ] 没有「功能正常」类空预期
- [ ] 动效与可验结果不写在同一编号里
- [ ] 清缓存、登录、平台与要跑的设备一致（iOS 不要写查 SIM）

### 7.7 生成草稿时的约束（给 QA 流程 / 模型）

产出 `draft_cases` 时强制：

1. `precondition` 只许 §2.1 的 kind；其余不要生成，或标人工、不进入自动跑。
2. `steps[]` 带 `num`；`expected_by_step` **只含需要校验的号**，不要为每个步骤自动编造预期。
3. 禁止按下标生成「步骤有几条预期就几条」。
4. 动词表、预期句式用 §7.3 / §7.4；超出则该条不要进自动回归包。

## 8. 落地顺序

**P0 记账**

- 前置 `unknown` / UNSUPPORTED → 跳过 + 标签，不挡跑；UNMET/FAIL 才停
- 步骤 / 预期对不上库 → `STEP.UNKNOWN` / `EXPECT.UNKNOWN`
- 每条写 `reason_code`；终态按 §1.2
- 看板增加三列 UNKNOWN 率

**P1 按号执行**

- `for n in step_nums`，预期只读 `expected_by_step[n]`
- **删除** `to_case_spec` 里「没有 by_step 就按下标取 expected_lines」
- 无 key → `EXPECT.SKIPPED.no_expect`
- 步骤成功后再跑该号预期

**P2** 自愈记 HEALED；布局分带用 dump bounds

## 9. 一句话

前置先跑完可执行项；库外 / 做不到跳过并打标签。步骤按号做，预期按号验，**缺号就不验**。只有真实执行和预期不符才挡任务 / 记产品红。
